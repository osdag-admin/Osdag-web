# Segment 13: Ops / Deployment / Testing infra — Claude Review
**Date:** 2026-08-01 | **Scope:** Dockerfile, docker-compose.yml, docker-compose.prod.yml, monitoring/, load_tests/, osdagweb.sh, requirements.txt, backend/apps/core/tests, root-level test_*.py, populate_database.py, diff_databases.py, .github/ | **Status:** Reviewed (read-only)

## Summary

This is the final segment of the 13-segment review. Ops/deployment plumbing is reasonably solid where it counts most (prod compose runs `DEBUG=False`, containers run as a non-root user, CI/CD secrets go through GitHub Actions `secrets.*` correctly, no PR-body injection risk in workflows). But there is one critical, repo-breaking finding: **`.env` — the file containing this deployment's real `SECRET_KEY`, DB password, Redis/Celery URLs, and other live credentials — is tracked in git**, not just present on disk. It was added in commit `ecf13dee` and has been modified twice since (most recently `ae064a7f`), meaning actual secret values are sitting in this repository's history regardless of whether `.env` is deleted from the working tree today. This compounds directly with Segment 1's finding that `SECRET_KEY`/`DATABASE_PASSWORD`/`INFLUXDB_TOKEN` all have hardcoded insecure fallbacks in `backend/config/*.py` — here we find the *actual* values these fallbacks were meant to guard against leaking are themselves committed. A second, lower-severity but repo-wide finding: the same `INFLUXDB_TOKEN` value (`osdag-super-secret-token`) is hardcoded in plaintext in three separate files (`docker-compose.yml` ×2 services, `monitoring/metrics_collector.py` fallback default), and Grafana is configured for unauthenticated anonymous viewer access on its exposed port. On the positive side, root-level `test_*.py`/`diff_databases.py`/`test_desktop_osdag.py` mentioned as possibly-stale in the review plan **no longer exist** — that cleanup already happened — and the `backend/apps/core/tests/` suite is genuinely good: it directly tests the auth-verification-gating behavior (guest/unverified/verified) that Segment 1 flagged as security-critical.

Closing note carried forward from Segments 5–12: a dead-code pattern (`*OutputDock.jsx` components with broken import paths, superseded by `EngineeringModule` → `BaseOutputDock` + config objects) was independently confirmed in **9 of 9** application module segments reviewed. This is not this segment's scope to re-verify (frontend module code), but given it is universal across every module checked, it is effectively certain to be a leftover from a single pre-refactor commit and worth a single bulk-delete pass across the whole `frontend/src/modules/*` tree rather than fixing it module-by-module.

## Red Flags (security / correctness-critical)

- **`.env` (real secrets) is tracked in git, not just present on disk** — root `.env`, confirmed via `git ls-files -- .env` (tracked) and `git log --oneline -- .env` (3 commits: added in `ecf13dee`, modified in `95f222f2` and `ae064a7f`). The root `.gitignore` does list `.env` (line near the end of the file), but gitignore rules only apply to *untracked* files — once a file has been `git add`ed, later listing it in `.gitignore` does nothing to remove it from history or stop future commits from tracking further edits to it. Concrete failure: anyone with clone/read access to this repository (or its history, even after a future `git rm .env`) can recover the real `SECRET_KEY`, database credentials, and any other value ever committed to this file, by running `git log -p -- .env` or checking out an old commit. If this repo is or ever becomes public, or if access is broader than intended, this is a full credential compromise, not a hypothetical one. Fix requires two separate steps: (1) rotate every credential that has ever been in this file (Django `SECRET_KEY`, DB password, any API keys/tokens), since removing the file going forward does not invalidate already-leaked values; (2) purge it from git history (e.g. `git filter-repo` — notably already a project dependency in `requirements.txt:103`) and stop tracking it (`git rm --cached .env`), then rely solely on the existing `.gitignore` entry for future commits. Per this review's own instructions, the file's contents were not read or printed — only its git-tracking status was checked — but the presence of real committed values here is inferred with high confidence from the fact that `.gitignore` explicitly names it and Segment 1 found matching insecure code-level fallbacks for the exact same keys.

- **Same `INFLUXDB_TOKEN` hardcoded in plaintext in 3 separate files** — `docker-compose.yml:56` (`backend` service), `docker-compose.yml:104` (`celery_worker` service), `monitoring/metrics_collector.py:47` (`os.getenv("INFLUXDB_TOKEN", "osdag-super-secret-token")` fallback) — all three use the identical literal string `osdag-super-secret-token`. This is the same token Segment 1 flagged as a hardcoded fallback in `backend/config/settings.py:284`; here it's confirmed to be duplicated in the ops layer too, not just as a Django settings fallback. Whoever provisioned this stack either never overrode the default via env var, or the "real" token in production *is* this literal string — either way, anyone who reads this repo's `docker-compose.yml` (which, unlike `.env`, is clearly meant to be committed) gets a working InfluxDB admin token if the deployed instance still uses defaults. `docker-compose.prod.yml` does not reference InfluxDB/Grafana at all (the observability stack in `docker-compose.yml` looks dev/staging-only), which somewhat limits blast radius, but the token should still not be a literal in a tracked file.

- **Grafana exposed with anonymous viewer access enabled** — `docker-compose.yml:165,169-170` — `ports: "3001:3000"` combined with `GF_AUTH_ANONYMOUS_ENABLED: "true"` and `GF_AUTH_ANONYMOUS_ORG_ROLE: Viewer`. The comment on line 169 (`# allow LAN users to view without login`) indicates this is intentional for convenience, but `ports:` (not `expose:`) publishes 3001 to whatever the host's network reachability is — if the host running `docker-compose.yml` is anything other than a fully isolated dev laptop (e.g. a shared staging box with a routable IP), this makes the full load-test/system dashboards (`monitoring/grafana/provisioning/dashboards/osdag_load_test.json`) viewable by anyone who can reach that port, no credentials needed. Also note `GF_SECURITY_ADMIN_PASSWORD: osdag_grafana` (line 168) and InfluxDB's `DOCKER_INFLUXDB_INIT_PASSWORD: osdag_password_123` (line 146) are both hardcoded weak passwords committed in the same file — lower severity since these are admin creds behind the anonymous-viewer-only door, but still real, guessable, committed passwords for services with `ports:` exposure.

- **CORS_ALLOWED_ORIGINS hardcodes specific developers' LAN IP addresses** — `backend/config/settings.py:47-57` (`'http://192.168.1.9:5173'`, `'http://10.104.135.9:5173'`, `'http://10.186.46.253:5173'`, alongside the expected `localhost`/`127.0.0.1` entries) — and this exact hardcoded list is asserted byte-for-byte in `backend/apps/core/tests/test_api.py:20-31` (`test_setUp`), which is what surfaced it in this segment's scope. This isn't a live secret, but it's a real ops/config smell worth flagging alongside Segment 1's settings.py findings: `CORS_ALLOWED_ORIGINS` is not environment-driven at all (no `os.getenv` wrapping, unlike `DEBUG`/`ALLOWED_HOSTS`/`SECRET_KEY` elsewhere in the same file), so every deployment ships with three named individuals'/machines' home or office IP addresses baked into the CORS allowlist, and the test suite now locks that list in place — any future change to `CORS_ALLOWED_ORIGINS` (e.g. removing a stale IP, or properly moving it to an env var) will break `test_setUp` and require a matching test edit, which will likely just perpetuate the pattern rather than prompt fixing it.

## Bugs

- **`populate_database.py` runs on every single `backend`/`celery_*` container start, not just first boot** — `docker-compose.yml:68`, `docker-compose.prod.yml:60`, and every celery worker's `command:` in prod chains `python manage.py migrate && python populate_database.py && exec gunicorn/celery ...`. `populate_database.py:26-32` does guard against re-seeding via a `SELECT count(*) FROM public."Bolt"` existence check, so it's not currently harmful, but this means the raw SQL dump file (`osdag_core/data/ResourceFiles/Database/postgres_Intg_osdag.sql`) gets opened, read, and `cursor.execute()`'d as one giant statement on every container restart/redeploy before the guard check even matters for performance — for `docker-compose.prod.yml`, this runs redundantly in the `backend` service AND is duplicated in effect (each of `celery_worker_calc`/`_cad`/`_reports`/`celery_beat` also depend on `db`/`redis` health but their `command:` fields don't call `populate_database.py`, only `backend`'s does — so this specific concern is actually fine, only `backend` runs it). Restating: not a functional bug, but worth noting the guard clause is the only thing preventing this from being a real problem on every redeploy.

- **`populate_database.py` broad exception swallowing hides all failure modes identically** — `populate_database.py:44-45` — `except Exception as e: print('Database population error:', e)`. A missing SQL file, a malformed connection string, a permissions error, and a genuine SQL syntax error in the seed data all produce the same non-fatal `print()` and the script exits 0 (no `sys.exit(1)`/`raise`). Combined with the compose `command:`'s `&&` chaining, this means if population silently fails, the chain still proceeds to `migrate`'s already-completed state and then to `gunicorn`/`celery` startup — the app comes up looking healthy with an empty/partial `Bolt` table, and the only trace is a line in container logs nobody is likely watching at deploy time.

## Code Quality / Improvement Suggestions

- **Dev vs. prod compose files have drifted beyond intentional differences** — `docker-compose.yml` runs 1 combined `celery_worker` consuming all 4 queues (`calculations,cad,reports,celery`) with `--concurrency=18`, while `docker-compose.prod.yml` splits into 4 dedicated workers (`celery_worker_calc`, `_cad`, `_reports`, plus `celery_beat`) with per-queue concurrency tuning (18/8/4) and `--max-tasks-per-child=10` on the CAD worker only. This is a reasonable prod optimization, but it means dev environments can't catch queue-starvation or per-queue-concurrency bugs before they hit prod, and the two Celery invocations are maintained as fully separate strings with no shared source of truth — a queue rename or new queue addition has to be manually kept in sync across both files (and `osdagweb.sh:101`, which has a third independent copy of the same `-Q calculations,cad,reports,celery` argument for the bare-metal dev path).

- **`requirements.txt` mixes pinned and unpinned versions inconsistently** — e.g. `requests==2.32.5` (pinned) next to `aiohttp`, `PyGithub`, `loguru`, `lxml`, `PyQt5` (all unpinned) in `requirements.txt:34,107,88,92,75`. For a repo that otherwise pins security-sensitive packages carefully (`cryptography==46.0.3`, `PyJWT==2.10.1`), leaving ~15 packages floating means CI (`ci.yml:86`, plain `pip install -r requirements.txt`) and prod Docker builds (`Dockerfile:25`) are not guaranteed to reproduce the same dependency graph on two different days, which can silently change behavior or introduce a vulnerable transitive dependency between builds with no corresponding code change to bisect against.

- **`git-filter-repo` is a runtime dependency** — `requirements.txt:103` (`git-filter-repo==2.47.0`) — this is a git-history-rewriting tool, not something any request-serving code path should need at runtime; it's presumably a one-off maintenance tool (notably, the exact tool needed to fix the `.env`-in-git-history issue above) that ended up in the main dependency list instead of being run ad-hoc or listed in a dev-only requirements file. Shipping it in the production image adds attack surface / image bloat for no runtime benefit.

- **`osdagweb.sh` has no service-readiness ordering** — `osdagweb.sh:100-127` — starts Celery, then `sleep 1`, then Django, then `sleep 1`, then Vite, using bare `sleep 1` as a synchronization proxy instead of an actual readiness check (e.g. polling Django's port before starting Vite, matching the pattern CI already uses in `ci.yml:49-61` for Postgres). On a slow machine or heavily loaded CI-like environment, `sleep 1` is not guaranteed to be enough for Django to finish `migrate`-adjacent startup work, so this local dev script could intermittently report "All services are running!" before they actually are. Low severity since it's dev tooling with visible logs to debug against, not a deploy-blocking issue.

## Minor / Nits

- **Commented-out `metrics-collector` service left in `docker-compose.yml`** — `docker-compose.yml:180-203` — an entire service definition (23 lines) is commented out rather than removed or extracted to a docs note explaining why it's disabled. If it's meant to be re-enabled later, a one-line comment explaining the reason it's currently off (and what needs to happen to turn it back on) would help; as-is it reads as abandoned code left mid-edit.
- **Inconsistent Redis/Celery URL literals vs. env indirection** — `docker-compose.yml`/`docker-compose.prod.yml` both hardcode `REDIS_URL: redis://redis:6379/0` etc. directly (not `${REDIS_URL:-...}`) while every other credential-shaped variable in the same block does use the `${VAR:-default}` pattern. Not wrong (these really are fixed by the compose network topology), but the inconsistency makes it harder to tell at a glance which values are meant to be overridable in a given deployment.
- **`load_tests/README.md` hardcodes a specific internal IP as the example target** (`http://10.104.135.9:8000`, same IP that shows up in `CORS_ALLOWED_ORIGINS` and in committed Locust HTML reports like `Locust_2026-06-23-14h32_...9_8000_10users.html`) — confirms load tests were run against an internal/private (10.x) address, not a public production endpoint, which is the safe pattern the review plan asked to confirm. No fix needed, just noting this checked out fine. The committed `.html` load-test report artifacts and `__pycache__/` under `load_tests/` are build/test output that arguably shouldn't be committed at all (repo bloat), though they carry no sensitive data beyond the same already-internal IP.
- **`load_tests/venv/` and `monitoring/.venv/` are real, large virtualenvs present on disk** but correctly excluded from git (`git ls-files` returns 0 hits for both — covered by their own auto-generated per-directory `.gitignore` and the root `**/.venv` pattern respectively). - **Root-level `test_*.py`, `diff_databases.py`, `test_desktop_osdag.py`** — mentioned in `REVIEW_PLAN.md` as possibly-stale desktop-app-era leftovers to check — **none of these exist in the current tree** (confirmed via `find . -maxdepth 1 -iname "*desktop*"` and `-iname "diff_databases*"`, both empty). ## Positive Notes

- **Dockerfile runs as a dedicated non-root user** — `Dockerfile:29-33` (`useradd -u 8888 deployuser`, `chown -R`, `USER deployuser`) — a correctly-applied hardening step that's easy to skip and often isn't in projects this size.
- **`docker-compose.prod.yml` does not expose `db`/`redis` ports to the host at all** (`expose:` used for `backend`, no `ports:` for `db`/`redis`), unlike the dev compose file which maps `db` to host port 5433 — correct tightening for the production topology.
- **`backend/apps/core/tests/test_email_verification.py` and `test_gdpr_compliance.py` are genuinely good, targeted security tests** — they directly exercise the exact auth-gating behavior (`guest` / `authenticated-but-unverified` / `verified`) that Segment 1 flagged as a security-critical area, using mocked Firebase tokens rather than real network calls, and `test_gdpr_compliance.py` specifically verifies that account deletion cascades correctly to `Project` and `UserAccount` records — this is the kind of test that would have caught a regression in the `OpenOsiById` null-`owner_email` IDOR-adjacent issue Segment 1 flagged, had it been extended to cover that path too.
- **CI correctly waits for Postgres readiness with a real socket-connect poll loop** (`ci.yml:49-61`) rather than a blind `sleep`, in contrast to `osdagweb.sh`'s local dev script noted above.
- **CD workflow's secret handling is clean** — `cd.yml:54-56` uses `secrets.SERVER_HOST`/`SERVER_USER`/`SERVER_SSH_KEY` correctly scoped through `appleboy/ssh-action`, and neither workflow interpolates any untrusted user-controlled string (PR title/body/branch name) directly into a `run:` shell step, so there's no GitHub Actions script-injection risk of the classic `${{ github.event.pull_request.title }}` kind.
