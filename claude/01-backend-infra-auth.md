# Segment 1: Backend infra & auth — Claude Review

**Date:** 2026-07-31 | **Scope:** `backend/apps/core/*`, `backend/config/*`, `backend/apps/sections/*` | **Status:** Reviewed (read-only)

## Summary

The Firebase-based authentication core (`middleware/firebase_auth.py`) and the main project-ownership CRUD (`project_api.py`, `delete_account_api.py`) are solid: proper token verification, cache-with-TTL, and consistent ownership scoping by server-derived email. However, `config/` ships multiple real hardcoded secrets (Django `SECRET_KEY`, a live SMTP account/password, a default DB password, an InfluxDB token), `DEBUG`/`ALLOWED_HOSTS` default insecurely when env vars are absent, `django-silk` is mounted with no visible access control, and there's a path-traversal bug in CAD file download. Two auth-adjacent endpoints (`/jwt/home`, `/googlesso/`) are live but will 500 on every call due to a dict/set typo. Overall: the auth core is well-built, but the surrounding config/ops layer has several concrete, fixable holes.

## Red Flags (security / correctness-critical)

- **Django `SECRET_KEY` hardcoded and committed** — `backend/config/secret_key.py:2` — `get_secret_key()` returns a literal `django-insecure-...` string used as the fallback whenever the `SECRET_KEY` env var isn't set (`settings.py:32`). If this repo is public (or the env var is ever missing in a deployment), anyone can forge session cookies, password-reset tokens, and any other Django-signed value. Should be removed entirely and the app should fail to start without `SECRET_KEY` in the environment.
- **Hardcoded live SMTP credentials committed in source** — `backend/config/utils.py:1-5` — `FROM_EMAIL = "osdagoncloud3@outlook.com"`, `PASSWORD = "osdag.developer"` in plaintext. This is a real credential leak regardless of whether the code path is currently used (see Bugs — it's dead code, but the credential is still exposed in git history/on disk).
- **Hardcoded DB password fallback** — `backend/config/postgres_credentials.py:9-10` (`get_password()` returns `"password"`) and duplicated inline in `settings.py:156` (`os.getenv('DATABASE_PASSWORD', PASSWORD or 'password')`). Weak, guessable default used whenever env vars are missing.
- **Hardcoded InfluxDB token default** — `backend/config/settings.py:284` — `INFLUXDB_TOKEN = os.getenv('INFLUXDB_TOKEN', 'osdag-super-secret-token')`.
- **`DEBUG` defaults to `True`** — `backend/config/settings.py:40` — `os.getenv('DEBUG', 'True')`. Any deployment that forgets to set `DEBUG=false` silently runs with Django debug pages (full stack traces, settings dump, source snippets) exposed to the internet.
- **`ALLOWED_HOSTS` defaults to `['*']`** — `backend/config/settings.py:44` — same failure mode: a missing env var silently opens the app to any Host header (host-header poisoning, cache-poisoning-adjacent attacks).
- **No `SECURE_*` hardening settings anywhere in `settings.py`** — no `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_HSTS_SECONDS`, `SECURE_PROXY_SSL_HEADER`. Even in a correctly-configured prod deployment (`DEBUG=false`), cookies and forced-HTTPS are not enforced at the Django layer.
- **`django-silk` mounted with no visible access control** — `backend/config/urls.py:13` (`path('silk/', include('silk.urls', ...))`), `silk` is in `INSTALLED_APPS` and `SilkyMiddleware` is active (`settings.py:97,105`), but there is no `SILKY_AUTHENTICATION` / `SILKY_AUTHORISATION` setting anywhere in `settings.py`. Django-silk's default behavior when both are unset/`False` is to serve its profiling UI — full request/response bodies, SQL queries, headers (including `Authorization: Bearer <token>`) — to **anyone** who can reach `/silk/`. This is a significant data-exposure risk if deployed as-is.
- **Path traversal / arbitrary file read in CAD download** — `backend/apps/core/api/cad/cad_model_download.py:13-40` — `section` and `request_id` come straight from `request.data` and are concatenated unsanitized into a filesystem path (`f"output-{section.lower()}.obj"` / `f"{request_id}_{section}.{format_type.lower()}"`) that's then opened and streamed back via `FileResponse`. Only `format_type` is allowlist-checked; `section`/`request_id` are not checked for `..`/path separators, so a value like `section="../../../../etc/passwd"` can escape `frontend/public/` or `file_storage/cad_models/`. `CADDownload` has no `permission_classes` override, so under the project-wide default (`IsEmailVerifiedIfAuthenticated`, which explicitly allows guests) this is reachable **without authentication**.

## Bugs

- **`JWTHomeView` / `GoogleSSOView` return a `set` instead of a `dict` — both will 500** — `backend/apps/core/api/auth/jwt_api.py:20` (`content = {'message' , 'Welcome to the JWT Authentication page'}`) and `backend/apps/core/api/auth/google_sso_api.py:14` (`Response({'message' , 'GoogleSSO under development'} , ...)`). Comma instead of colon makes these 2-element Python `set` literals, not dicts. DRF's renderer will raise on trying to JSON-serialize a `set`, so both routes (`GET /jwt/home`, `GET /googlesso/`, both live in `backend/apps/core/urls.py:33-34`) throw an unhandled exception on every call.
- **`GoogleSSOView` is guest-reachable but non-functional** — no `permission_classes` override means it falls back to the global default `IsEmailVerifiedIfAuthenticated`, which explicitly allows unauthenticated requests (`apps/core/permissions.py:35-38`). Combined with the bug above, any anonymous caller hitting `/googlesso/` triggers an unhandled server exception.
- **`OpenOsiById` ownership check silently no-ops when `owner_email` is null** — `backend/apps/core/api/projects/osi_api.py:88-93` — `if owner_email and requester_email != owner_email: return 403`. Since `OsiFile.owner_email` is `blank=True, null=True` (`apps/core/models.py:43`), any row with no owner bypasses the check entirely, letting any authenticated user read it by iterating the auto-increment `osifile_id`. Currently latent — a repo-wide grep found no call site that does `OsiFile.objects.create(...)`, so no code path populates this table today — but the guard is a landmine: the first future write path that doesn't explicitly set `owner_email` reintroduces an IDOR silently.
- **`config/mailing.py` ships a hardcoded OTP fallback of `123`** — `backend/config/mailing.py:7` (`def send_mail(email, OTP=123)`), and logs the SMTP password to stdout (`mailing.py:19`, `print('password : ', PASSWORD)`). This function is unused anywhere in the current codebase (dead code — email verification is actually handled by Firebase, per `email_verified` claims in `firebase_auth.py`), but it's still live source shipping a real credential and an insecure default. Should be deleted, not left in place.

## Code Quality / Improvement Suggestions

- **Inconsistent logging** — most of `apps/core/api/*` (`project_api.py`, `osi_api.py`, `jwt_api.py`, etc.) uses bare `print()` for debug output, including printing user emails and full request payloads (`project_api.py:47,60,81,180-181`), while `delete_account_api.py` and `export_data_api.py` correctly use the `logging` module. `print()` output bypasses log levels/rotation and is easy to leave enabled in production; standardize on `logger`.
- **Overly broad exception handling that masks failure types** — the `except Exception as e: return JsonResponse({'success': False, 'error': str(e)}, status=400)` pattern is repeated throughout `project_api.py` and `osi_api.py`. This turns e.g. a database outage or a programming error into a client-facing "400 Bad Request" with the raw exception text exposed — both misleading to API consumers and to any monitoring that alerts on status codes, and a minor info-disclosure of internals.
- **Dead, commented-out auth checks left in place** — `project_api.py:21-22, 130-131, 226-227, 264-265, 303-304` all have a commented-out earlier version of the guest-check directly above the live one. Harmless today, but it's the kind of leftover that invites someone to uncomment/merge the wrong branch later. Delete rather than comment out.
- **Duplicate source of truth for DB credentials** — `postgres_credentials.py` hardcodes defaults, and `settings.py:154-159` re-hardcodes the same fallback (`'password'`, `'osdagdeveloper'`, etc.) a second time instead of relying solely on env vars with no insecure fallback.
- **Blanket `csrf_exempt` on all project/OSI views** — expected for a Bearer-token API, but applied per-view (`@method_decorator(csrf_exempt, name='dispatch')` on every class) rather than centrally; easy to forget on a new view.

## Minor / Nits

- `jwt_api.py` and `google_sso_api.py` read as leftover FOSSEE-fellowship-era scaffolding, fully superseded by `firebase_auth.py`. Given both are broken (see Bugs), consider deleting rather than leaving stub/broken endpoints live and routed.
- `jwt_api.py:2` — comment typo "Atharva Pinagle" vs the "Pingale" spelling used elsewhere (cosmetic only).

## Positive Notes

- `FirebaseAuthentication` (`middleware/firebase_auth.py`) is well-built: verifies tokens via `firebase_admin`, caches successful validations keyed by `sha256(token)` with a TTL matched exactly to the token's own `exp`, checks `user.is_active`, and keeps `UserAccount` in sync for backward compatibility.
- `DeleteAccountAPIView` (`delete_account_api.py`) does a clean, correctly-scoped hard delete (Firebase user + `Project` + `OsiFile` + Django `User`) inside `transaction.atomic()`, with proper `logger` usage and `permission_classes = [IsAuthenticated, IsEmailVerified]`.
- `ProjectAPI` / `ProjectDetailAPI` / `ProjectByNameAPI` consistently scope every query by `user_email` derived from the authenticated `request.user` (never from client input), which avoids IDOR on the main project CRUD surface — a good pattern that `osi_api.py`'s `OpenOsiById` should have followed as strictly.
- `osi_files.py` avoids unsafe YAML deserialization by hand-rolling a minimal flat-YAML reader instead of calling `yaml.load`/`yaml.safe_load` — a deliberate and reasonable choice given the input is user-uploaded.

## Open Questions

- Did not fully trace how user-supplied report-customization content reaches the `pdflatex` invocation in `report_customization_api.py` (subprocess call itself is safe — fixed argv list, no `shell=True`/string interpolation — but LaTeX itself can read/leak files via `\input`/`\openout` if user content flows unescaped into the `.tex` source). Worth a dedicated follow-up pass on LaTeX injection specifically.
- Given the volume (~90 files), several files were skimmed or not opened in depth: `apps/sections/validation.py`, `options_merge.py`, `core/registry.py`, `module_finder.py`, `main_registry.py`, `consumers.py`/`routing.py` (websocket/Channels layer), `signals.py`, `tasks.py` (Celery). Recommend a targeted follow-up on `consumers.py`/`routing.py` (auth on websocket connections) and `tasks.py` (Celery task input validation) since neither was covered here.
- Could not verify from source alone whether `/silk/` is blocked at a reverse-proxy layer in actual deployments — flagged as a red flag based on the Django-level config having no restriction, but infra-level mitigations may exist outside this repo.
