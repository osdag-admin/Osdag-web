# Segment 4: Shared hooks/config/context/utils — Claude Review

**Date:** 2026-07-31 | **Scope:** `frontend/src/modules/shared/{hooks,config,context,utils}` (19 hooks, 2 context files, 3 config files, 10 utils files) | **Status:** Reviewed (read-only)

## Summary

This layer is the connective tissue for every engineering module (form state, design submission, CAD export, OSI save/load, PSO optimization, navigation guards). Overall quality is solid — careful `AbortController`/generation-counter usage in the async hooks, a clean reducer for dock layout, and thoughtful legacy-format handling in the OSI loader. The two most consequential issues are both performance/correctness bugs stemming from unmemoized objects: an unmemoized Context provider value that will re-render the entire module tree on every state change, and an unmemoized service object whose reference instability triggers duplicate autosave network calls. There's also a fragile "sentinel value" technique for reverse-engineering OSI key mappings that can silently drop fields, and a chunk of OSI/CAD-export logic duplicated between a hook and a component.

## Red Flags (security / correctness-critical)

**Context value object not memoized — causes full-tree re-renders on every state change** — `frontend/src/modules/shared/context/EngineeringContext.jsx:600-696` — `EngineeringProvider` builds a single `value` object with 100+ properties (form state, hover position, docks, PSO data, handlers) inline on every render, and passes it directly to `<EngineeringContext.Provider value={value}>` with no `useMemo`. Every consumer of `useEngineeringContext()` (output dock, CAD viewer, forms, dropdown menus — effectively the whole module page) re-renders whenever *any* single piece of this state changes, including `hoverText`/`hoverPos` which update on every 3D-model mouse-move via `handleHoverLabel` (`useHover.js:7-13`). Concrete failure: hovering over the CAD model to see a part label re-renders every form field, the output dock, and every dropdown in the page on each mouse-move event. Fix would be `useMemo(() => ({...}), [/* deps */])`, likely splitting hover state into its own context so high-frequency updates don't fan out.

**`useEngineeringService` returns a fresh object every render → spurious duplicate autosave requests** — `frontend/src/modules/shared/hooks/useEngineeringService.js:34-379` — every function is individually wrapped in `useCallback`, but the object literal returned at the bottom (`return { getModuleData, createDesign, ... }`) is a new reference on every call/render (no `useMemo` wrapping the return). This `service` is passed into `useDesignSubmission(service, moduleConfig)` (`useEngineeringModule.js:89`), whose unmount-flush effect depends on `[projectId, service]` (`useDesignSubmission.js:61-74`). Because `service` changes identity every render, that effect's **cleanup** fires on almost every re-render — not just unmount. Concrete failure scenario: a design is calculated, the 5s-debounced autosave queues a `pendingSaveRef.current` payload (`useDesignSubmission.js:247-273`), and the user keeps interacting with the page (any state change → re-render) before the 5s timer fires — each such re-render calls `service.updateProject(projectId, pendingSaveRef.current)` again with the *same stale* payload, without clearing `pendingSaveRef.current`. This produces redundant `PUT /api/projects/:id/` calls and risks a stale payload overwriting a more recent save if responses complete out of order. Root cause is `useEngineeringService` needlessly being a hook at all — it holds no state and could be a plain exported module of functions, or its return value wrapped in `useMemo(() => ({...}), [])`.

## Bugs

**WebSocket reconnect exhaustion leaves UI silently stuck** — `frontend/src/modules/shared/hooks/useWebSocketOptimization.js:118-129` — on `ws.onclose` with a non-1000 code, the hook retries up to `MAX_RECONNECT_ATTEMPTS = 3` with exponential backoff. Once `reconnectAttemptsRef.current >= 3`, the `if` guard is false, so no further reconnect is scheduled — but `onError` is never called in that branch either. `isConnected`/`isOptimizing` are already `false` from the `onclose` handler, so the PSO optimization dashboard has no way to distinguish "still trying" from "permanently failed"; the user sees a stalled progress UI with no error message. Add an `onError` call (or equivalent status flag) once retries are exhausted.

**OSI key-mapping tracer can silently drop fields** — `frontend/src/modules/shared/utils/osiMapperTracer.js:55-70` — `getModuleKeyMap` reverse-engineers the OSI-key ↔ React-input-key mapping by dry-running each module's `buildSubmissionParams` with sentinel strings (`"__TRACER_VAL__:<key>"`) and checking which output values still start with that prefix. Any `buildSubmissionParams` implementation that transforms the value in a way that breaks the prefix — e.g. `Number(...)` coercion (silently `NaN`, no throw) or a global string replace — causes that key to be silently omitted from `keyMap`, with only a swallowed `catch` and a comment ("Gracefully continue to next pass", line 67-69). A concrete example of this exact transform pattern already exists in the codebase: `osiInputSerializer.js:67` does `inputs?.bolt_type?.replaceAll('_', ' ')`, which — if the same transform is applied to a value inside any module's `buildSubmissionParams` — would turn `"__TRACER_VAL__:bolt_type"` into `"__TRACER VAL__:bolt type"`, failing the `startsWith("__TRACER_VAL__:")` check and dropping that field from the map. Net effect: loading a saved OSI file could silently fail to restore specific fields for whichever modules hit this, with no error surfaced anywhere. Worth auditing per-module `buildSubmissionParams` (out of scope for this segment) for exactly this pattern.

**`convertToCSV` throws on null/undefined values** — `frontend/src/modules/shared/utils/moduleUtils.js:4-12` — `values[index].toString()` (line 8) is unguarded; if `data` contains any key with a `null`/`undefined` value, this throws a `TypeError` instead of exporting an empty cell.

**Inconsistent `alert()` vs `message.error()` for user-facing errors** — `frontend/src/modules/shared/hooks/useDesignSubmission.js:185,216`, `frontend/src/modules/shared/hooks/useEngineeringModule.js:198,211` — most of the codebase uses antd's non-blocking `message.error(...)` toast, but these four call sites use the native blocking `alert()`/native browser dialog instead, which halts JS execution and looks jarringly out of place next to the rest of the UI.

## Code Quality / Improvement Suggestions

**Duplicated OSI/CAD-export logic between a component and shared hooks** — `frontend/src/modules/shared/utils/UnifiedDropdownMenu.jsx:65-113` (`loadInput`), `:126-168` (`saveInput`), `:221-287` (CAD export switch) largely re-implement `useOsiFileHandlers.js`'s `handleLoadInputFromShortcut`/`handleSaveInputs` and `useCadExport.js`'s `exportCadByType` almost line-for-line (same base64→Blob→download dance, same format map). Two parallel implementations of the same logic risk drifting apart when one is fixed and the other isn't. `UnifiedDropdownMenu` also calls `useEngineeringService()` independently (line 49), compounding the unmemoized-service issue above.

**`UnifiedDropdownMenu.jsx` is a full React component living under `utils/`** — same file — it has JSX, local state (`useState`), and effects; it belongs in `components/`, not `utils/`, which otherwise contains plain functions.

**`ModuleContext.jsx` is not actually a context** — `frontend/src/modules/shared/context/ModuleContext.jsx:1-3` — it's a 3-line re-export barrel (`export { createDesign } ...`), despite the filename and directory suggesting a React Context provider like its sibling `EngineeringContext.jsx`. Misleading for anyone navigating by filename.

**Dead commented-out config block** — `frontend/src/modules/shared/config/designPrefModuleConfig.js:474-493` — an entire earlier version of the `"SeatedAngleConnection"` config is left commented out immediately above the live version at line 494; should be deleted.

**Ad-hoc `setTimeout` used to let state "settle" before re-submitting a design** — `frontend/src/modules/shared/context/EngineeringContext.jsx:394` — `await new Promise((resolve) => setTimeout(resolve, 100));` inside `handleSubmitEnhanced` is a magic-number sleep hoping prior `clearDesignResults()`/`resetModuleState()` state updates have flushed before the next submission starts; fragile under slower renders (low-end devices, background tabs). Consider awaiting an explicit "reset complete" signal instead.

**Effects with `eslint-disable-next-line react-hooks/exhaustive-deps`** — `EngineeringContext.jsx` has 6 such suppressions (e.g. lines 220, 292, 299, 365, 379, 418). Each individually looks deliberate, but the density is a maintainability smell — worth a periodic re-audit to confirm none have accumulated a real stale-closure bug as the file has grown.

**`useProjectLoader.js`'s `callbacksRef` pattern lacks an explanatory comment** — `frontend/src/modules/shared/hooks/useProjectLoader.js:32-76` — deliberately keeps most callbacks in a ref and out of the main effect's dependency array (`[projectIdFromUrl, user, loading, designCompletedRef]`, line 194) to avoid re-running on every callback identity change. Reasonable pattern, but easy for a future edit to add a new *directly referenced* (non-ref) variable without updating the dependency array, silently reintroducing staleness. A short comment on the effect would help.

## Minor / Nits

**Verbose `console.log` on every WebSocket event** — `frontend/src/modules/shared/hooks/useWebSocketOptimization.js` (lines 40, 46, 66, 75, 82, 98, 102, 115, 123, 149, 161, 176) — logs connection URL, every PSO update, iteration/particle indices, etc. unconditionally. Other hooks in this same folder gate their `console.error` behind `import.meta.env.DEV` (e.g. `useDesignSubmission.js:68`, `:266`); this hook should follow the same convention to avoid noisy production consoles.

**Project name silently mutated before save, without showing the user** — `frontend/src/modules/shared/hooks/useProjectCreation.jsx:43` — `projectName.replace(/\s+/g, '_')` turns "My Project" into "My_Project" with no preview/confirmation of the final name.

## Positive Notes

- `useDesignPrefSync.js` and `useProjectLoader.js` both use `AbortController` + a request-generation counter to correctly discard stale in-flight responses — the right pattern for async data fetched off changing inputs, and applied consistently.
- `useDockPanels.js` is a clean, well-contained reducer for a fairly intricate responsive layout state machine (desktop vs. mobile dock toggling rules).
- `osiNormalizer.js`/`osiLoader.js` handle both the current nested `{dock, pref}` format and older flat OSI formats gracefully, with sensible fallback key-cleaning heuristics.
- Timeout/interval/event-listener cleanup is consistently correct across `useViewport.js`, `useWebSocketOptimization.js`, `useDependentData.js`, `usePlateGirderOptimization.js` — no leaked listeners or intervals found.

## Open Questions

- Does the PSO WebSocket endpoint (`ws/optimize/plate-girder/`, built in `useWebSocketOptimization.js:25`) require authentication? No token/credential is attached to the WebSocket handshake anywhere in this segment. PSO optimization is compute-heavy (Celery task per the comment in `EngineeringContext.jsx:162`); if the backend channel consumer doesn't independently enforce auth, this could be a DoS vector. Worth cross-checking against the Segment 1 (backend infra & auth) review.
- Is `useEngineeringService`'s per-render re-creation intentional, or should it simply be moved out of the hooks pattern entirely (it wraps no component state, only stable imported functions)?
