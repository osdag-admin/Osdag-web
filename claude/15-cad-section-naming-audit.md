## Why this needed its own pass

The 13-segment review (see `00-cross-cutting-summary.md`) already flagged that CAD-generation code is duplicated per module. This pass goes one level deeper: it traces the literal *strings* used to identify a CAD part ("Model", "Beam", "Plate", "Connector", "EndPlate", "cleatAngle", …) across every place that string has to match another one for the CAD viewer to work, and compares the result against the desktop app's own naming (`osdag/src/osdag_gui/`, plus the underlying `osdag_core` design-type classes it calls into).

**Finding: there are 4 independent, hand-maintained lists of "valid CAD sections" per module, not one.** They are supposed to agree but don't always:

1. **`frontend/.../configs/*Config.js`** — `cadOptions: [...]` — drives which buttons render in the CAD viewer UI.
2. **`frontend/src/modules/shared/components/cad/config/viewMappings.js`** — `DEFAULT_VIEW_MAPPINGS` — a manually maintained bridge table mapping each UI button label to the (possibly differently-named) backend mesh names it should match. This is what actually papers over most of the naming drift described below.
3. **`backend/apps/core/utils/cad_helpers.py`** — `SECTION_MAPPINGS` — the *live* default list of sections the backend actually generates during a design run, used whenever the frontend doesn't explicitly send its own `sections` list (confirmed: it never does — see below).
4. **Each submodule's own `adapter.py`** — a hardcoded allowlist (`valid_sections = (...)` or `if section not in (...)`) inside `create_cad_model()` that the *generation* call is validated against.

There's also a **5th, dead copy**: `backend/apps/core/api/cad/cad_model_api.py`'s `CADGeneration` view has its own hardcoded per-module section list, baked into a long `if/elif` chain. This view is still routed (`/api/design/cad`, `/api/design/cad/` in `backend/apps/core/urls.py:65-66`) but **no frontend code calls it** (verified via repo-wide grep) — it's an orphaned, reachable-but-unused endpoint, in the same "dead but still live" category as the orphaned `cantilever` submodules found in Segments 9 and 11 of the main review. Its docstring even says "Accepts GET requests" while defining a `post()` method — a small extra sign of how stale it is. Its own hardcoded list (`cad_model_api.py:94-119`) is the direct ancestor of #3 above — `cad_helpers.py`'s module docstring literally says *"Extracted from legacy cad_model_api.py for reuse in new module-based endpoints"* — but the extraction wasn't a byte-for-byte copy in every case (see the Purlin/Struts finding below), so the two have already drifted from each other too.

**Confirmed: the frontend never sends its own `sections` list.** `trigger_async_cad()` (`backend/apps/core/utils/module_helpers.py:198-221`) does `sections = request.data.get('sections'); if not sections: sections = get_default_sections(...)`, and a repo-wide grep of the frontend for a `sections` field sent to any CAD-generation call found none — every design run relies entirely on backend list #3 (`SECTION_MAPPINGS`) to decide what actually gets generated. This means list #1 (`cadOptions`, what the user sees as buttons) and list #3 (what actually gets generated) are **not the same mechanism gated by the same data** — they can silently diverge, and in a few places they already have.

## Confirmed dead / guaranteed-failing CAD options

These aren't naming cosmetics — they're buttons or generation attempts that don't work, verified by cross-referencing all 4 lists plus (where relevant) the desktop source.

- **Tension Member (`bolted` and `welded`, both submodules): the 4th CAD section "Endplate" is generated on every single design run and is guaranteed to fail.** `backend/apps/core/utils/cad_helpers.py:36-37` — `SECTION_MAPPINGS['tension-member']['bolted'|'welded'] = ['Model', 'Member', 'Plate', 'Endplate']`. But both adapters' own allowlist (`tension_member/submodules/{bolted,welded}/adapter.py:208-209` / `:178-179`) is `("Model", "Member", "Plate", "Connector")` — **"Endplate" is not in it.** `Service.get_cad_model()` (`bolted/service.py:81-93`) is a bare passthrough to `create_cad_model()` with no local try/except, so the `InvalidInputTypeError` it raises propagates up into `generate_cad_models()`'s per-section loop (`cad_helpers.py:135-168`), which does catch it — so this doesn't break Model/Member/Plate, but it does mean **every tension-member design run spends a Celery task cycle attempting, and permanently failing, a 4th CAD generation call**, logged into a `error_details` list the frontend never reads (frontend `cadOptions` for both TensionMembers configs only lists 3 items — `["Model", "Member", "Plate"]`, confirmed via `boltedToEndConfig.js:19` / `weldedToEndConfig.js:18` — "Endplate" was never even offered as a UI button). Corroborating evidence this was never meant to be live: the **desktop app's own `get_3d_components()`** for the equivalent class (`osdag/src/osdag_core/design_type/member.py:3429-3444`) has the exact same 4th option commented out in its own source: `# t3 = ('Endplate', self.call_3DEndplate)` — it was disabled on desktop too, and whoever built `SECTION_MAPPINGS` for the web app copied the *method name* (`Endplate`) without noticing it was dead code on the reference implementation. Fix: drop `'Endplate'` from both `SECTION_MAPPINGS` entries — pure waste removal, zero UI impact since nothing has ever displayed it.

- **Struts Bolted's frontend offers a "Plate" CAD button that the backend never generates by default.** `frontend/src/modules/compressionMember/configs/strutsBoltedConfig.js:16` — `cadOptions: ["Model", "Member", "Plate"]` — but `cad_helpers.py:49` — `SECTION_MAPPINGS['compression-member']['struts-bolted'] = ['Model', 'Member']` — only 2 items, no `"Plate"`. (Contrast with the sibling `struts-welded` entry on line 50, which does include `'Plate'` — and also still carries the same dead `'Endplate'` waste as tension_member.) Whether clicking "Plate" in the Struts Bolted CAD viewer shows anything depends on whether the "Model" section's part-manifest (`cad_helpers.py:186-195`, the `.parts.json` sidecar generated alongside "Model") happens to include an individually-named "Plate" part regardless of whether "Plate" was separately requested as a top-level section — that manifest's contents come from `osdag_core`, which is out of scope for this review, so this is flagged as **plausible, not confirmed**, unlike the Tension Member finding above which is confirmed via a direct, unambiguous allowlist mismatch.

- **Purlin's frontend offers a "Beam" CAD button; both the backend default-sections list and the adapter's own allowlist reject it.** `frontend/src/modules/flexuralMember/purlin/configs/purlinConfig.js:18` — `cadOptions: ["Model", "Beam"]` — but `cad_helpers.py:42` — `SECTION_MAPPINGS['flexure-member']['purlin'] = ['Model']` (no "Beam"), **and** the adapter itself (`flexure_member/submodules/purlin/adapter.py:415`) — `if section not in ("Model",): raise InvalidInputTypeError(...)` — rejects "Beam" outright even if it were requested directly. Same caveat as above about whether "Model"'s manifest independently surfaces a "Beam"-named part applies, but here there's the additional fact that a *direct* request for `section="Beam"` (e.g. via a future "export this part" feature) would hard-fail, which isn't true for the Struts Bolted case above.

## Naming drift that "works" today only because of a manual bridge table (fragile, not currently broken)

- **`EndPlate` (frontend/UI) vs `Connector` (backend generation + validation) — 3 modules.** `beamBeamEndPlateConfig.js:8`, `columnColumnEndPlateConfig.js:6`, `beamToColumnEndPlateConfig.js:8` all use `cadOptions: [..., "EndPlate"]` as the UI button label. But the actual backend section that gets generated and validated is `"Connector"` — confirmed in `SECTION_MAPPINGS['moment-connection']['beam-beam-end-plate'|'beam-column-end-plate'|'column-column-end-plate']` (`cad_helpers.py:23,24,27`, all list `'Connector'`, none list `'EndPlate'`) and in each adapter's own allowlist (`beam_beam_end_plate/adapter.py:311`, `beam_column_end_plate/adapter.py:386`, `column_column_end_plate/adapter.py:317` — all check for `"Connector"`, not `"EndPlate"`). The only reason clicking "EndPlate" in the UI actually shows the right part today is `viewMappings.js:16` — `"EndPlate": ["EndPlate", "Connector", "Bolt", "Bolts", "Weld", "Welds"]` — a manually-maintained array that explicitly lists "Connector" as one of the mesh names the "EndPlate" button should match. If this one line in `viewMappings.js` is ever edited (or the module's own `viewMappings` override is added, which bypasses the default per `createViewMapper`'s logic at `viewMappings.js:43`) without someone remembering *why* "Connector" is in that array, the button silently breaks. This is a UI-label-vs-internal-key split that **the desktop app has too** (see next section) — Osdag-web didn't invent the "EndPlate" vs "Connector" split, but it did add a 4th independent list that has to agree with it, where desktop only ever had 2 (a checkbox label and one internal string).

- **`CleatAngle` (frontend, capital-C PascalCase) vs `cleatAngle` (backend, camelCase) — case mismatch.** `frontend/src/modules/shearConnection/cleatAngle/configs/cleatAngleConfig.js:9` — `cadOptions: [..., "CleatAngle"]`. Backend: `SECTION_MAPPINGS['shear-connection']['cleat-angle']` (`cad_helpers.py:16`) and the adapter's own allowlist (`cleat_angle/adapter.py:496`) both use `"cleatAngle"` (lowercase c). This does **not** currently break anything end-to-end, for two reasons: (1) generation always uses the correct backend-side casing since the frontend never sends its own `sections` list (see above), so the actual mesh gets correctly generated and named `"cleatAngle"`; (2) `viewMappings.js`'s `createViewMapper` does a case-insensitive fallback match (`viewMappings.js:67-71`) when no exact match is found, so the UI button showing "CleatAngle" still correctly matches a mesh named "cleatAngle". It's flagged here purely as a latent-risk naming inconsistency: it works only because of a case-insensitive matching path that exists for unrelated reasons, not because anyone made the two names agree on purpose.

- **`Cover Plate` vs `CoverPlate` (with/without space) coexist across different module families.** Simple Connection's butt/lap-joint modules use `"Cover Plate"` (with a space — `butt_joint_bolted/adapter.py`'s `valid_sections`, matching desktop's `butt_joint_bolted.py` label exactly), while the Moment Connection cover-plate family uses `"CoverPlate"` (no space) throughout its own 4 modules' `cadOptions`/`SECTION_MAPPINGS`/adapter allowlists. Each family is internally consistent, so this isn't a live bug, but it means the CAD viewer's part-name convention isn't uniform across the codebase, and `viewMappings.js:18` has to carry *both* spellings in the same array (`"CoverPlate": ["CoverPlate", "Cover Plate", "Connector", ...]`) to bridge them.

## Comparison against the desktop app's canonical naming (`osdag/src/osdag_gui` + `osdag_core/design_type/**/get_3d_components()`)

The desktop app defines, per design-type class, a `get_3d_components()` method returning `[(UI checkbox label, handler function), ...]`; each handler calls `commLogicObj.display_3DModel(<internal key>, ...)`. This is the closest thing to a "ground truth" naming reference, and it turns out **the desktop app already has the UI-label-vs-internal-key split** that Osdag-web inherited — Osdag-web's problem isn't that it invented this pattern, it's that it turned a 2-list problem (label + 1 internal key) into a 4-list problem (label + viewMappings bridge + default-sections list + adapter allowlist) per module:

## Recommendation

This is a naming/config-hygiene problem, not an engineering-calculation problem — none of this touches `osdag_core`. The core issue is architectural: **4 hand-maintained lists per module (5, counting the dead legacy one) where 1 would do.** Concretely:

1. Delete the dead `cad_model_api.py` `CADGeneration` view and its URL routes (`api/design/cad`, `api/design/cad/`) — confirmed zero frontend callers, and its hardcoded section table is already stale relative to its own descendant (`SECTION_MAPPINGS`).
2. Remove the two confirmed-dead phantom sections: `'Endplate'` from `SECTION_MAPPINGS['tension-member']['bolted'|'welded']`, and consider whether `struts-bolted`'s missing `'Plate'` entry (or the adapter-only `'Connector'`/`'Column'`/`'Girder'`/`'Beam'` entries with no reachable caller anywhere) should be added for consistency or removed as unreachable, module by module.
3. Longer-term: make `cadOptions` (the frontend, user-visible list) the single source of truth, and have the backend either (a) derive `SECTION_MAPPINGS` from it at request time — the frontend already knows this list and currently just never sends it, so the simplest fix is literally to start sending `moduleConfig.cadOptions` as the `sections` field on the CAD-generation request, which `trigger_async_cad()` already supports as an override — or (b) generate a single canonical JSON/constants file shared by both frontend and backend at build/import time so the two can't drift. Either approach collapses today's 4 independent lists down to 1–2, and would have prevented every finding in this report.
