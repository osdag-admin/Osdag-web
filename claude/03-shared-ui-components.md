# Segment 3: Shared UI components — Claude Review
**Date:** 2026-07-31 | **Scope:** frontend/src/modules/shared/components/{cad,diagrams,help,outputDock} + root-level shared components | **Status:** Reviewed (read-only)

## Summary

This is the CAD viewer (Three.js/react-three-fiber), SVG diagram, output-dock, and root-level form/modal component library shared by every engineering module (~13.5K lines, `EngineeringModule.jsx` alone is 1,727 lines). The CAD stack (`SceneManager`, `CadScene`, `SmartPart`, `CadSceneBbox`) is well-engineered overall — careful `useMemo`/`useCallback` usage, WebGL context-loss recovery, and a real (if partial) disposal effect for loaded geometry. The most concrete issues found: a per-part edge-geometry/material leak in `SmartPart` that's never disposed, several `dangerouslySetInnerHTML` sinks fed by backend-sourced (and in one case plausibly user-influenced) strings, a `normalizedCadModelPaths` "memoization" in `EngineeringModule.jsx` that doesn't actually preserve referential stability, and a `ReportCaptureDev` debug helper that installs `window.*` globals unconditionally in production.

## Red Flags (security / correctness-critical)

- **`dangerouslySetInnerHTML` fed by backend-derived hover labels** — `frontend/src/modules/shared/components/EngineeringLayout.jsx:399` and `frontend/src/modules/shared/components/EngineeringModule.jsx:1624` — the CAD hover tooltip renders `hoverText` via `dangerouslySetInnerHTML`. `hoverText` ultimately comes from `hoverDict` (`useEngineeringModule.js:276`, `cadData?.hover` — the design-calculation API response), which is looked up per-part in `SmartPart.jsx:78-114` and passed up through `onHover`/`handleHoverLabel`. Section designations shown in these labels can originate from user-uploaded data: `XlsxImportTrigger.jsx` lets a user import a custom `.xlsx` section table, and `inserted_designations` (free-text strings from the uploaded file, e.g. `Columns`/`Beams`/`Angles`/`Channels` designation columns) become selectable section options that flow into design inputs and, plausibly, back out into `hover` labels in the design response. If the backend doesn't strip HTML from that designation string (out of scope for this segment — see Segment 1 for backend validation coverage), a designation like `<img src=x onerror=alert(document.cookie)>` would execute when hovered over the CAD model. Even if this specific path turns out to be sanitized server-side, using `dangerouslySetInnerHTML` for any backend-echoed string is fragile — a single future field addition to `hover` that includes free text (project notes, custom material grade, etc.) silently reopens this. Recommend switching to plain text rendering (React auto-escapes) unless the label genuinely needs HTML markup, in which case sanitize with a library like DOMPurify.
- **`dangerouslySetInnerHTML` for output-dock field labels** — `frontend/src/modules/shared/components/outputDock/OutputModalLayouts.jsx:23,128,169,194,227,279,334,389,423` — nine call sites render `field.label` via `dangerouslySetInnerHTML`, presumably to support superscript/subscript units (e.g. `mm&sup2;`). These labels currently come from static per-module config (out of this segment's scope to fully verify), so risk is low today, but it's the same pattern repeated nine times — a single module config that ever derives a label from user/backend input (e.g. a customized report field name) would be exploitable. Worth centralizing into a small `<UnitLabel html={...}/>` component so the risk surface is one place, not nine.

## Bugs

- **`SmartPart`'s edge geometry/material is never disposed — genuine memory leak** — `frontend/src/modules/shared/components/cad/SmartPart.jsx:35-46` — `edgesVisuals` (`THREE.EdgesGeometry` + `THREE.LineBasicMaterial`) is created in a `useMemo` keyed on `[geometry, showEdges, name]`, but nothing calls `.dispose()` on the previous value when the memo recomputes (e.g. when `geometry` changes because the user switches CAD view/model) or when the component unmounts. `SceneManager.jsx`'s cleanup effect (lines 121-125) only disposes the `disposables` array collected during the *initial* STL/OBJ parse — it has no knowledge of the derived edge geometries created inside child `SmartPart` instances. Concrete failure: repeatedly switching between CAD views (Model → Beam → Column → …) or re-running a design (which remounts `SceneManager` per `modelKey`) accumulates orphaned `EdgesGeometry`/`LineBasicMaterial` GPU buffers that are never freed, growing GPU memory over a long session until the tab crashes or WebGL context is lost (which `CadViewer.jsx:33-39` does partially recover from, but the underlying leak keeps growing on every recovery too).
- **`normalizedCadModelPaths` "memoization" does not preserve reference stability — the whole optimization is a no-op** — `frontend/src/modules/shared/components/EngineeringModule.jsx:181-194` — the code builds `out`, stringifies it, compares against `prevPathsRef.current`, and on a cache hit returns `JSON.parse(nextStr)` instead of a cached object reference. `JSON.parse` always allocates a brand-new object, so `normalizedCadModelPaths` is a new reference on literally every render regardless of whether the underlying data changed — the `prevPathsRef` comparison achieves nothing except wasted `JSON.stringify`/`JSON.parse` work. Any downstream `useEffect`/`useMemo` keyed on `[normalizedCadModelPaths, ...]` (e.g. the debug effect at line 197-201, and effectively `CadViewer`'s remount key at `CadViewer.jsx`'s `key={\`${modelKey}-${selectedSection}\`}` doesn't use it directly but other consumers may) will re-fire on every parent re-render, not just when CAD paths actually change. Fix: either return the previous object reference on a cache hit (store the actual object, not its JSON string) or drop the memoization attempt entirely since it isn't achieving its goal.
- **`ReportCaptureDev` installs `window.captureReportViews`/`downloadReportViews`/`setCameraToTopView` unconditionally, including in production** — `frontend/src/modules/shared/components/cad/ReportCapture.jsx:93-193`, mounted unconditionally inside every `CadScene` render via `CadViewer.jsx:139` (`<ReportCaptureDev />`, no `import.meta.env.DEV` gate). Despite the name and comment ("Development helper"), this ships to production and exposes camera-manipulation/screenshot globals on `window` for any page script (including an XSS payload, tying back to the red flag above) to call. Low severity on its own, but it's dead weight in the prod bundle and an unnecessary attack-surface increase if any injection vector is ever found elsewhere on the page.
- **CAD model-part matching is case-sensitive-then-inconsistently-normalized, silently drops parts named `"model"` twice** — `frontend/src/modules/shared/components/cad/SceneManager.jsx:49-111` — `uniqueKeys` dedupes `modelPaths` case-insensitively via `findIndex`, but then the loop iterates `Object.entries(modelPaths)` (the *original*, non-deduped object) and only checks `uniqueKeys.includes(key)` for exact-case membership. If a backend response ever contains both `"Model"` and `"model"` keys (case variants), only the exact-case survivor of the dedup lands in `uniqueKeys`, and the other's `dataUrl` is silently skipped without a warning — could produce an incomplete CAD render with no user-visible error.

## Code Quality / Improvement Suggestions

- **`XlsxImportTrigger`'s table-picker `<input type="radio">` uses `useId()` in the `name` attribute but the component can mount many times per page (once per Import button)** — `frontend/src/modules/shared/components/XlsxImportTrigger.jsx:34,203` — this is actually done correctly (unique `name` per instance avoids radio-group collisions), noted as a positive pattern worth calling out, not a bug — flagging only because it's an easy thing to break if refactored without noticing why `useId()` is there.
- **Duplicated grouped-field layout logic across 5 `OutputModalLayouts` components** — `frontend/src/modules/shared/components/outputDock/OutputModalLayouts.jsx:39-54,247-261,302-316,366-371` — `CapacityComplexLayout`, `CleatBoltCapacityLayout`, `CleatSectionCapacityLayout`, and `SeatedSectionCapacityLayout` all reimplement the identical `fields.reduce(...)` "group by `field.section`" logic. Extracting a single `groupFieldsBySection(fields)` helper would remove ~40 lines of duplication and guarantee the grouping behavior can't drift between layouts.
- **`SmartPart`'s `PART_ALIASES` hover-label resolution is a large, deeply-nested heuristic chain (lines 61-114) reverse-engineering which `hoverDict` key corresponds to a mesh name** — this mirrors the same "sentinel-tracer" fragility documented in Segment 4's review of `osiMapperTracer.js`. Sixteen-plus fallback branches (exact match → lowercase → capitalized → singular/plural → semantic alias → "Bolt vs Plate" sanity override) all silently degrade to showing the raw mesh `name` if none match, with no logging. Worth consolidating into a single lookup table built once per design response rather than recomputed heuristically per hover.
- **`normalizedCadModelPaths` duplicates every key three ways (`trimmed`, lowercase, uppercase)** — `EngineeringModule.jsx:183-189` — for a model with N parts this triples the object size held in state/memory and passed through props on every render, to work around inconsistent casing from the backand (confirmed also needed in `CadViewer.jsx:94-102`'s manual case-fallback lookup for `EndPlate`/`CoverPlate` → `Connector`). Fixing the backend to emit consistent casing (or normalizing once at the API boundary in a data-source layer, not per-component) would remove the need for this defensive tripling in multiple places.
- **`convertToCSV`-style `.toString()` pattern isn't present here, but similarly-unguarded assumptions exist**: `CustomMaterialModal.jsx:55-58` calls `parseInt(inputs.fy_20)` etc. without a radix-safety concern (radix 10 default is fine) but also without clamping — `parseInt("20abc")` silently yields `20` instead of rejecting the input, since `validateInput` (line 144-154) uses `isNaN(value)` on the *string* `"20abc"` which correctly catches that specific case (good), but `parseInt("20.9")` silently truncates to `20` with no warning to the user that their decimal yield-stress input was rounded down — worth surfacing rather than silently truncating a structural material property.

## Minor / Nits

- `CadViewer.jsx:34-39` `handleContextLost` remounts the entire `Canvas` (via `canvasKey` bump) on WebGL context loss, which is a reasonable recovery strategy, but there's no user-visible notification that a recovery happened — a silent full CAD re-render could be confusing if it happens mid-interaction (e.g. mid-drag orbit).
- `InputSection.jsx:292-340` (`renderNumericInput`)'s manual digit-filtering `onChange` handler duplicates logic that native `<input type="number">` (or a numeric-mask library) would give for free, and it still permits pathological strings like `"--"` or `"1.2.3"` partially through intermediate render states before the regex fully normalizes them — not a crash risk since `setInputs` just stores the string, but worth a unit test given it feeds structural engineering parameters.
- `help/AboutOsdagModal.jsx:43,68,70,72` also uses `dangerouslySetInnerHTML` for `ABOUT_HTML`/`LICENSE_HTML`/`PRIVACY_HTML`/`CAVEATS_HTML` — these are static developer-authored constants (confirmed by naming/usage pattern), so no injection risk, just flagging for completeness since it showed up in the same grep as the higher-risk sinks above.

## Positive Notes

- `SceneManager.jsx`'s model-loading effect (lines 38-126) correctly guards against setting state after unmount (`isMounted` flag) and disposes the STL/OBJ geometries it directly parses — the leak identified above is specifically in the *derived* edge geometry created downstream in `SmartPart`, not in the base loading path.
- `CadViewer.jsx`'s WebGL `webglcontextlost` handling (lines 33-39, 67-72) is a real, working recovery mechanism — many Three.js integrations skip this entirely and just show a permanently black canvas after a GPU driver reset.
- `CadSceneContext.jsx` is a small, correctly-memoized context (`useMemo` on `value`, line 13-16) — a good contrast to the unmemoized `EngineeringContext` flagged in Segment 4.
- `WeldDiagram.jsx` and the other SVG diagram components consistently guard against non-finite/empty numeric props via a shared `toNum(v, fallback)` pattern (`WeldDiagram.jsx:25-29`) and render an explicit "dimensions unavailable" fallback rather than a broken/NaN SVG.

## Open Questions

- Does the backend ever echo raw user-supplied strings (custom section designations from `XlsxImportTrigger` imports, custom material grades, project/design names) into the `hover` dict returned by the design-calculation API? This segment couldn't confirm from the frontend alone since the backend serialization is out of scope here — flagging for Segment 1 (or a follow-up) to check `apps/core/utils/osi_files.py` / the design-response serializers for whether `hover` values are sanitized or pass through user input verbatim. If they do pass through verbatim, the `dangerouslySetInnerHTML` red flag above becomes a confirmed stored-XSS vector rather than a plausible one.
- Is `ReportCaptureDev` intentionally shipped to production (e.g. for support/debugging live customer sessions via console), or was the `import.meta.env.DEV` gate simply forgotten? Worth a one-line confirmation from whoever added it.
