# Segment 2: Frontend app shell & site infra — Claude Review
**Date:** 2026-07-31 | **Scope:** `frontend/src/{Auth,homepage,context,constants,components,utils,datasources}` | **Status:** Reviewed (read-only)

## Summary

This layer is generally clean: Firebase auth flows are readable, `apiClient.js` has sensible 401-retry/token-refresh logic, and route/endpoint constants are centralized. The main issues are (1) a large chunk of dead legacy state (`GlobalState`/`AppReducer`/`catalogDataSource`) still mounted at the app root, (2) `convertToCSV` reimplemented near-identically in three different files across this segment and segment 4, and (3) a few rough edges in error handling and guest/session UX rather than anything security-critical. No secrets are hardcoded here (the Firebase client config is meant to be public — see note below).

## Red Flags (security / correctness-critical)

- **`ProjectAuthGuard` only protects the URL, not data access** — `frontend/src/components/ProjectAuthGuard.jsx:19-22` — guests hitting a `/:projectId` route get client-side redirected to the guest path, but this is purely a UX nicety; if a guest calls the underlying API directly with a guessed/known `projectId`, this component does nothing to stop it. Authorization must (and per Segment 1's findings, mostly does) live server-side — but it's worth confirming there's no assumption anywhere in this app-shell layer that reaching a route implies the user is authorized to see its data, since this guard gives that false impression.
- **No client-side session/idle timeout; Firebase ID tokens silently auto-refresh forever** — `frontend/src/context/AuthContext.jsx:13-19`, `frontend/src/utils/apiClient.js:37-65` — `onAuthStateChanged` keeps `user` set indefinitely and `apiClient` force-refreshes on any 401. Combined with tokens living in IndexedDB (Firebase SDK default, not this code's choice), a persistent XSS on this origin would have a long window to exfiltrate a live session, since there's no absolute session expiry enforced client-side. Low severity given no other XSS vector was found in this segment, but worth noting as defense-in-depth is absent.

## Bugs

- **`convertToCSV` implemented three times with diverging behavior** — `frontend/src/context/ModuleState.jsx:288-344` (`convertToCSV` inside `ModuleProvider`), `frontend/src/utils/csvUtils.js:6-56` (nearly byte-identical copy, exported standalone), and `frontend/src/modules/shared/utils/moduleUtils.js:4-12` (a third, much simpler version that a parallel review of Segment 4 found throws a `TypeError` on `null`/`undefined` values because it skips the null-guard the other two have). Three copies of the same logic that have already partially diverged is a maintenance hazard — a fix to the null-handling bug in one won't propagate to the other two. `useEngineeringService.js` calls into `csvUtils.js`'s copy while `ModuleState.jsx`'s `generateReport('csv', ...)` action is a separate, likely-now-unreachable code path (see next finding) — worth consolidating into a single shared utility.
- **`ModuleState.jsx`'s `generateReport('pdf'|'design_report', ...)` are dead stubs that always return an error** — `frontend/src/context/ModuleState.jsx:355-357,389-391` — both branches immediately return `{ success: false, error: 'Legacy ... removed. Use the in-app report modal.' }`. Only the `'csv'` branch does real work. If any caller still invokes `generateReport('pdf', ...)` expecting the old behavior, it will silently no-op with a returned error object that may not be surfaced to the user depending on the caller (not verified in this segment — the report-modal flow lives in Segment 3's `outputDock`). Dead code should either be removed or the callers updated to stop referencing it.
- **`Object.values(uniqueModulesMap)` de-dup in `MainContent.jsx` can silently drop legitimate distinct projects** — `frontend/src/homepage/components/MainContent.jsx:47-55` — projects are deduped by `project.submodule`, keeping only the most-recently-updated one per submodule. This is presumably intentional ("recently used modules" widget should show one entry per module type), but the same `projects` array (undeduped) is passed to `ProjectsListCard` for the "Recent Projects" panel, so the two panels use different data — worth confirming this asymmetry is intended UX and not a copy-paste slip from one list into the other.

## Code Quality / Improvement Suggestions

- **Dead legacy state tree still mounted at the app root** — `frontend/src/context/GlobalState.jsx` (full file, 88 lines) + `frontend/src/context/AppReducer.jsx` (full file, 54 lines) — `GlobalProvider` is mounted in `App.jsx:11` and wraps the whole app, but a repo-wide grep found `GlobalContext` is never imported/consumed anywhere outside `GlobalState.jsx` itself. This means `getInitialData`, `getDesignTypes`, `getSubDesignTypes`, `getLeafLevelDesignType` — and the `catalogDataSource` API calls they trigger (`fetchCatalogRoot`, `fetchDesignTypes`, etc., hitting the unauthenticated `osdag-web/...` catalog endpoints per `datasources/endpoints.js:99-108`) — are wired up but structurally unreachable UI-wise. This looks like the old (pre-registry) module-selection tree that's been superseded by `constants/modules.js` / `MODULE_SLUGS` (`constants/apiRoutes.js`). Safe to delete if confirmed unused, removing ~150 lines and a provider layer from the render tree.
- **`homepage/data/mockData.js` is unused dead code** — full file — `recentProjects` and `recentModules` are defined here but a grep for both names across `homepage/` only found `recentModules` used as a *local variable name* freshly computed from live API data in `MainContent.jsx:56` (different data, coincidental same name — not an import of this file). No file imports `mockData.js`. Safe to delete; keeping it around risks a future edit accidentally wiring it back in as a fallback for a real API-empty state.
- **Inconsistent error surfacing on API failures** — `frontend/src/homepage/components/MainContent.jsx:29-30,41-42` — both `fetchRecentProjects` and `handleDeleteProject` swallow errors with a bare `// swallow` / `// ignore` comment and no user-facing feedback beyond an implicit empty list. A failed delete in particular could look like "nothing happened" to the user rather than "the delete failed" — worth at least a toast (the codebase already uses `react-toastify` per `App.jsx:62`).
- **`LoginPage.jsx` has heavy `console.log`/`console.error` instrumentation left in** — `frontend/src/Auth/LoginPage.jsx:228,230,240-246`, and similarly `utils/firebaseAuth.js:49,55,57,125,129,132,134,138`, `datasources/authDataSource.js` (indirectly) — logs email addresses, backend error payloads, and full error objects to the browser console in production builds (no `import.meta.env.DEV` gate, unlike the guarded logs in `ModuleState.jsx:243,254`). Low sensitivity (client-side console, user's own data) but inconsistent with the DEV-gating pattern used elsewhere in the codebase, and unnecessary noise/minor info leakage in prod.
- **`handleGuestSignIn` has a pointless try/catch** — `frontend/src/Auth/LoginPage.jsx:208-219` — the only statement in the `try` block is `navigate('/home')`, which cannot throw in a way the `catch` meaningfully handles; this is vestigial from an earlier version that probably called an API here.
- **Firebase client config (`apiKey`, `projectId`, etc.) is hardcoded in `Auth/firebase.js`** — `frontend/src/Auth/firebase.js:4-12` — this is standard/expected for Firebase web apps (these values are not secrets and are meant to be public; access is actually controlled by Firebase Security Rules and API key restrictions configured in the Firebase console, not by hiding this object). Flagging only so it's not mistaken for a leak during cross-review — worth confirming the Firebase console has HTTP referrer restrictions on this API key as defense-in-depth, but that's outside this codebase.

## Minor / Nits

- **`utils/auth.js` vs `utils/firebaseAuth.js` naming is confusing** — two same-directory files with near-identical names and overlapping concerns (`utils/auth.js` has read-only helpers like `getAccessToken`/`isGuestUser`; `utils/firebaseAuth.js` has the actual signup/login/reset actions). Not a bug, but easy to import the wrong one; a rename (e.g. `authState.js` vs `authActions.js`) would reduce confusion.
- **`ModuleState.jsx` still ships a no-op `SET_COOKIE_FETCH` action with a "Remove unused cookie action" comment** — `frontend/src/context/ModuleReducer.jsx:268-270` — the comment says to remove it, but the case (and presumably its dispatch call sites, not checked in this segment) is still present.
- **Commented-out dead `useEffect` left in `ModuleState.jsx`** — `frontend/src/context/ModuleState.jsx:523-526` — a commented-out effect referencing a no-longer-existent `populateModule` function. Should be deleted rather than left as a comment.
- **`LoginPage.jsx` imports `Link` twice via separate statements** — `frontend/src/Auth/LoginPage.jsx:8,20` (`AUTH` from endpoints is imported but appears unused in this file's visible logic — only `firebaseLoginWithToken` in `firebaseAuth.js` actually uses it) — and a stray commented-out import (`// import { useAuth } from '../hooks/useAuth';`, line 19). Minor housekeeping.
- **`constants/apiRoutes.js` has a commented-out dead map entry** — `frontend/src/constants/apiRoutes.js:42` (`// [MODULE_KEY_END_PLATE]: 'shear-connection/end-plate',`) superseded by the line below it — fine as a breadcrumb but could be removed once confirmed permanent.

## Positive Notes

- `apiClient.js`'s 401 → force-refresh-token → retry-once flow (`utils/apiClient.js:37-65`) is well-built: it correctly avoids infinite retry loops via the `isRetry` flag, degrades gracefully to sign-out + redirect on refresh failure, and preserves the original error type/shape (including `pending_deletion`/`uid` passthrough for account-deletion flows).
- `firebaseAuth.js`'s `syncUserToBackend` dedup logic (`utils/firebaseAuth.js:36-70`) correctly prevents redundant concurrent backend-sync calls for the same ID token using a module-level in-flight-promise cache — a subtle race condition handled correctly.
- Centralizing all backend paths in `datasources/endpoints.js` and all module→URL-slug mappings in `constants/apiRoutes.js` is a good pattern that should make backend route renames low-risk to propagate.
- `utils/shortcuts/ShortcutProvider.jsx` is a well-designed layered keyboard-shortcut engine (priority ordering, editable-target blocking, mac/non-mac combo handling) — solid, self-contained implementation.

## Open Questions

- Is `context/GlobalState.jsx` (and the `osdag-web/...` catalog endpoints it calls) truly dead, or is there a code path outside this segment's scope (e.g. an admin tool, or code not yet reviewed in segments 5-13) that still relies on it? Recommend confirming with a full-repo grep before deleting.
- Is the asymmetry between deduped (`recentModules`) and undeduped (`projects`) data feeding the two `MainContent.jsx` panels intentional?
- Should `LoginPage.jsx`/`firebaseAuth.js` console logging be gated behind `import.meta.env.DEV` for consistency with `ModuleState.jsx`'s pattern, or is verbose auth-flow logging intentionally always-on for support/debugging purposes?
